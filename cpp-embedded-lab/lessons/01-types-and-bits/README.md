## 1. 为什么不用 `int`

你可能觉得 `int` 就是 32 位。在你的电脑上是，但在 MCU 上不一定：

| 平台 | `sizeof(int)` | `sizeof(long)` |
|---|---|---|
| x86 / x64 (Windows/Linux) | 4 | 4 (Win) / 8 (Linux) |
| 经典 8/16 位 MCU (AVR, MSP430) | 2 | 4 |
| ARM Cortex-M | 4 | 4 |

所以 C++ 标准只保证 `int` **至少** 16 位。你在 x86 上写 `int` 溢出测试全过，
烧到 MSP430 上数据全变。这类 bug 极难查，因为**代码看起来完全正确**。

规矩：**只要这个数有明确的位宽含义，就用定宽整型。**

```cpp
#include <cstdint>

std::uint8_t  a;   // 0 ~ 255
std::uint16_t b;   // 0 ~ 65535
std::uint32_t c;   // 0 ~ 4294967295
std::int16_t  d;   // -32768 ~ 32767    ADC 采样值
std::int32_t  e;   //                   PID 中间量
```

什么时候可以用裸 `int`？循环变量、纯局部计数，而且上界很小。比如
`for (int i = 0; i < 8; ++i)` 完全没问题。判断标准是：
**这个值会不会参与位运算、跨模块传递、或者和硬件打交道？会就别用 `int`。**

`std::` 前缀可以省，写 `uint32_t` 也行。但 `std::` 版本更严谨，
而且能避免和某些 C 头文件里的宏撞名。

### 两个反直觉的点

```cpp
std::uint8_t x = 200;
x += 100;                 // x == 44，不是 300
```

无符号溢出是**良定义**的：按 2 的位宽取模回绕。所以编译器可以放心地
把 `x + 100 > x` 优化成 `true`（它知道不可能溢出）。

```cpp
std::int16_t y = 32767;
y += 1;                   // 【未定义行为 UB】不是回绕！
```

有符号溢出是 **UB**。标准没说会发生什么，编译器有权假设它不会发生，
于是优化掉你的溢出检查。**所以判断溢出必须在更宽的类型里做**（见第 5 题）。

## 2. 位运算：MCU 上的工作基本都是位运算

寄存器的每一位都有含义。比如某个 UART 控制寄存器：

```
bit  0      : 使能
bit  1      : 发送中断使能
bit  2      : 接收中断使能
bit  3      : 保留
bit  7:4    : 波特率分频选择      <- 4 位字段
bit  15:8   : 校验/停止位配置     <- 8 位字段
```

你要能：**只改 7:4 这 4 位，绝不碰其它位。**

三种基本操作，必须闭着眼写出来：

```cpp
reg |= mask;          // 置位：把 mask 里为 1 的位都设成 1
reg &= ~mask;         // 清位：把 mask 里为 1 的位都设成 0
reg ^= mask;          // 翻转
```

读写一个"字段"的标准模式：

```cpp
// 读：先右移到最低位，再掩码
value = (reg >> lsb) & mask;

// 写：先把目标位清零，再把新值放进去
reg = (reg & ~(mask << lsb)) | ((value << lsb) & (mask << lsb));
```

**注意那个 `& mask`**。少了它，`value` 的高位会串到相邻字段里去。
这是实际项目里最常见的低级 bug 之一，而且往往只在特定数值下才现形。

### 移位运算的两个 UB

```cpp
1u << 32        // UB：移位位数 >= 类型位宽
x  >> 32        // UB：同上
1  << 31        // 有符号左移溢出，别赌，用 1u

std::uint32_t m = 1u << 31;   // 安全：无符号左移是良定义的回绕
```

所以第 1 题 `make_mask(32)` 不能天真地写 `(1u << 32) - 1`。
**这个陷阱在真实项目里坑过很多人。**

## 3. 数 1 的个数：一个小而经典的问题

`popcount` 在嵌入式里比你想的常见：

* 实现 CRC、位图、优先级仲裁
* 统计中断标志寄存器里同时挂起了几个源
* 触摸按键 / 电容传感器的多点检测

朴素写法：循环 32 次，每次取一位。

更优雅的写法：

```cpp
while (v != 0) { v &= (v - 1); ++count; }   // 循环次数 = 1 的个数
```

为什么 `v & (v - 1)` 能消掉最低位的 1？拿几个数在纸上算一遍：

```
v         = 0b1100 (12)
v - 1     = 0b1011 (11)
v & (v-1) = 0b1000 (8)    最低位的那个 1 没了，高位全保留
```

还有 O(1) 的 SWAR 版本（位并行加法，约 12 条指令），以后有兴趣可以查
"SWAR popcount"。这一课先把循环版写对。

## 4. 饱和运算：不确定时，停在边界

嵌入式里没有"出错就抛异常"这回事。1 kHz 的控制回路里某个值算炸了，
代码还得继续跑。业界公选的策略是**饱和**：

```
回绕（默认行为）          饱和（你要实现的）
32767 + 1 -> -32768      32767 + 1 -> 32767
```

为什么饱和更好？想象电机电流环的积分项。一次回绕，输出从 +100% 跳到 -100%，
硬件可能就废了。饱和最坏是持续限幅，控制器还能收敛回来。

同样的道理适用于：PWM 占空比、ADC 采样、滤波系数、协议长度字段。

## 5. Q15 定点数：为什么 MCU 上不爱用 float

两个理由：

1. **贵。** 没有 FPU 的 Cortex-M0/M3 上，一次 float 乘法要几十到上百周期，
   还会悄悄链进一个浮点运算库（代码体积多几 KB）。
2. **不确定。** 浮点运算的时序不确定，对硬实时的中断服务程序是灾难。

替代方案是定点数，最常用的是 **Q15**：

```
存储值 = 实际值 × 32768

 实际值    存储值
 -1.0     -32768        （只有 -1.0 是恰好表示的）
 -0.5     -16384
  0.0          0
  0.5      16384
  1.0      不能表示（32768 超出 int16_t）
```

于是：

```cpp
// 加法：和整数加法一模一样
c = a + b;                       // 但要做饱和，见第 5 题

// 乘法：要去掉一个缩放因子
// (a/32768) * (b/32768) = (a*b) / 32768^2
// 我们要的是 Q15 结果，所以只需要再除以一次 32768：
result = (a * b) / 32768;        // 用 >> 15 实现
```

注意 **`a * b` 必须用 `int32_t` 装**：32767 × 32767 ≈ 2^30，
放进 `int16_t` 就废了。

再加上四舍五入（加半个 LSB 再移位），就是第 6 题。

## 6. `constexpr` 和 `static_assert`：把假设写进代码

`exercises.h` 开头有这两行：

```cpp
static_assert(sizeof(std::int32_t) == 4, "本工程假设 int32_t 是 4 字节");
```

这是**编译期**断言。哪天你的平台不满足这个假设，编译直接失败，
而不是等到现场跑出数据错乱。代价是零（编译后什么都不剩）。

`constexpr` 同理，表示"这个值编译期就能算出来"：

```cpp
constexpr std::uint32_t kUartTxReady = 1u << 0;   // 直接烧进 flash 的常量
constexpr std::uint32_t kUartBaudMask = 0xFu << 4;
```

嵌入式里非常好用的一个模式：**把寄存器地址和字段位置写成 `constexpr`，
再用 `static_assert` 交叉验证它们不自相矛盾。** 第 05 课会展开。

现在只需要养成两个习惯：

* 常量用 `constexpr`，不用 `#define`（`#define` 没有类型、没有作用域）
* 能编译期检查的，别留到运行期
